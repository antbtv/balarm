# plan-milestone

Цель: **ни одна строка кода этапа не пишется, пока не утверждён список задач.**

## Шаг 0. Определи этап
* Аргумент `$ARGUMENTS` (например `M1`). Если пусто — возьми первый этап из `docs/PRD.md` §8, у которого нет файла `docs/milestones/M<N>-*.md` со статусом `Done`.
* Если предыдущий этап не в статусе `Done` — сообщи пользователю и спроси, продолжать ли.

## Шаг 1. Собери контекст
Прочитай:
1. `docs/PRD.md`: строку этапа в §8, все FR/NFR, относящиеся к нему, §6 (архитектура), §9 (тесты).
2. `docs/adr/*` — принятые решения.
3. Предыдущий `docs/milestones/M<N-1>-*.md` — раздел «Перенесено» и «Уроки».
4. Текущее состояние кода (`settings.gradle.kts`, модули, что уже реализовано) — чтобы не планировать сделанное.

## Шаг 2. Архитектурная проработка
Вызови агента **architect** (Agent tool, `subagent_type: architect`) с задачей: «Спроектируй этап M<N>: <описание>. Дай модули/классы/контракты, порядок, риски, нужные ADR». Если он создал ADR со статусом `Proposed` — вынеси их в раздел «Решения на утверждение».

## Шаг 3. Декомпозиция на задачи
Правила:
* Задача = 0.5–4 часа работы, один логичный коммит, проверяемый результат.
* Каждая задача имеет: ID `M<N>-T<NN>`, заголовок, ссылки на FR/NFR, описание, **критерии приёмки** (проверяемые), тесты (какие), зависимости (ID), затрагиваемые модули, оценку (S/M/L).
* Порядок — по зависимостям; сначала модель/домен, потом данные, потом UI.
* Обязательные сквозные задачи в конце каждого этапа:
  * `T-test`: тестирование этапа агентом **tester** (+ сценарии R* из PRD §9.2, относящиеся к этапу).
  * `T-review`: ревью агентом **reviewer** всего этапа.
  * `T-docs`: обновить PRD/ADR/CLAUDE.md, если что-то поменялось.
* Отметь задачи, которые затрагивают надёжность будильника, меткой `🔔 reliability` — для них сценарии R* обязательны.
* **Feature flags:** каждая новая пользовательская фича получает флаг в `config/features.properties` (реестр — PRD §3.12) в первой же задаче, где появляется её код, со значением `false`; в `T-docs` этапа — включить завершённые фичи (`true`) и обновить реестр в PRD. Ядро надёжности (FR-FLAG-4) флагами не закрывается.
* Отметь UI-задачи (экраны, компоненты, навигация) меткой `🎨 ui` — их выполняет агент **ui-developer**. Отделяй UI от логики: сначала задача на домен/данные с контрактом, потом UI-задача, зависящая от неё.

## Шаг 4. Запиши план
Создай `docs/milestones/M<N>-<kebab-name>.md` по шаблону `docs/milestones/TEMPLATE.md` (статус `Planned`).

## Шаг 5. Утверждение — СТОП
Покажи пользователю краткую сводку: цель этапа, кол-во задач, таблица `ID | задача | оценка | зависимости`, решения на утверждение, риски. Спроси: «Утверждаешь план? Можно править задачи.»
* **Не начинай реализацию** в этом же ответе.
* Правки пользователя → обнови файл → снова покажи изменения.
* После явного «да/утверждаю» → поставь статус `In progress`, дату утверждения, и предложи начать с первой задачи через скилл `implement-task`.

## Шаг 6. Ведение этапа (по мере работы)
* После каждой задачи — отметить `[x]` и commit sha в таблице.
* Новые найденные задачи — добавлять в раздел «Добавлено по ходу» с пометкой, а не молча.
* Этап `Done`, когда: все задачи `[x]`, отчёт tester без critical/major, вердикт reviewer ✅/⚠️, DoD из PRD §8 выполнен. Заполни «Уроки» и «Перенесено».
