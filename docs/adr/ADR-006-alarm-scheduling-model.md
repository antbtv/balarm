# ADR-006: Модель планирования: расчёт момента, идентичность PendingIntent, перепланирование, snooze

## Status
Accepted (2026-10-03, реализовано и проверено в M1). Предложено 2026-09-29.

## Context
* FR-REL-1: только `setAlarmClock`. FR-REL-4: время = локальное время + дни; DST: несуществующее 02:30 → **03:00**, дублированное → первое наступление. Поведение `java.time` по умолчанию для gap — сдвиг на длину разрыва (02:30 → **03:30**), т.е. не совпадает с PRD.
* `AlarmManager` сбрасывает всё при перезагрузке; ресиверы (ADR-001 §3) перепланируют. Несколько ресиверов могут прийти почти одновременно (`TIME_SET` + `TIMEZONE_CHANGED`, `LOCKED_BOOT_COMPLETED` + `BOOT_COMPLETED`).
* Перенос из M0: `AlarmId` требует `value > 0`, а Room `autoGenerate` использует 0 как «нет id»; `requestCode` у `PendingIntent` — `Int`, id — `Long`.
* Телефон может быть выключен/перезагружаться ровно в момент будильника; ADR-002 §5: «вот-вот наступивший» будильник ставится на `now + несколько секунд`.
* Время в домене — через инжектируемый `java.time.Clock` (CLAUDE.md). `Clock.systemDefaultZone()` **фиксирует зону при создании**: синглтон после смены TZ продолжил бы считать в старой зоне.

## Decision
1. **Идентификатор.** `AlarmId(value: Long)`, инвариант `value >= 0`; `AlarmId.UNSAVED = AlarmId(0)`, `isSaved = value > 0`. Несохранённый `Alarm` имеет `UNSAVED`; репозиторий возвращает выданный id. Планировщик и движок работают только с сохранёнными (`require(id.isSaved)`). Таблица с `AUTOINCREMENT` → id не переиспользуются.
2. **Один `setAlarmClock` на будильник.** Идентичность `PendingIntent` задаётся **data URI** `balarm://alarm/<id>` (участвует в `Intent.filterEquals`) → коллизии невозможны при любом `Long`. `requestCode = 0`. Флаги `FLAG_IMMUTABLE or FLAG_UPDATE_CURRENT` (экстры `scheduledFor`, `kind` обновляются). `showIntent` → главный экран (через `AlarmUiIntents`, см. ADR-007). Отмена — тем же URI + `FLAG_NO_CREATE`.
3. **Расчёт момента** — `NextTriggerCalculator` (`:core:domain`, чистая функция): ближайший момент **строго после** `after` для `LocalTime` (секунды = 0) и набора `DayOfWeek` (пусто = разовый: сегодня, если ещё впереди, иначе завтра). Локальная дата-время → `Instant`:
   * gap (нет валидных offset'ов) → **instant перехода** `rules.getTransition(ldt).instant` (02:30 → 03:00 нового времени);
   * overlap → **ранний** offset (первое наступление); второе наступление никогда не считается кандидатом, поэтому повторный звонок в 02:30 после отката часов невозможен.
   * Дата, целиком отсутствующая в зоне (напр. Pacific/Apia 2011-12-30), пропускается — будильник этого дня не звонит (задокументировано тестом).
4. **Clock.** В DI — `SystemZoneClock` (`:core:domain`): `instant() = Instant.now()`, `getZone() = ZoneId.systemDefault()` на каждый вызов. Платформа обновляет `TimeZone.getDefault()` в живом процессе при смене зоны. `Clock.systemDefaultZone()` в продакшн-коде запрещён (чек-лист reviewer).
5. **Runtime-состояние** (ADR-004 `alarm_runtime`): `nextTriggerAt` = ровно то, что отдано `setAlarmClock`; `nextTriggerKind`:
   * `REGULAR` — очередное наступление по расписанию;
   * `SNOOZE` — `now + interval` (абсолютный `Instant`, DST не влияет);
   * `CATCH_UP` — догоняющий звонок после пропуска (п. 7).
   Экстра интента `kind` дополнительно допускает `RESUME` (ADR-007 п. 7) — он не персистится и не меняет runtime.
   Эффективный триггер: не-`REGULAR` с `nextTriggerAt` в будущем (или в пределах `LATE_GRACE`) имеет приоритет над расписанием, иначе — `REGULAR` из калькулятора (если `enabled`).
6. **Срабатывание.** При `onFired` в одной транзакции: `lastFiredAt = now`; `snoozeCount` сохраняется для `SNOOZE`, иначе = 0; разовый → `enabled = false`; повторяющийся → **сразу** планируется следующий `REGULAR` (падение звонка не теряет завтрашний будильник). Если экстра `scheduledFor` старше `LATE_GRACE` (часы переведены вперёд, AlarmManager отдал «просроченный» alarm) — не звонить, перепланировать (M7: уведомление «пропущен», FR-REL-6). Если БД недоступна/исключение — **звонить** с настройками по умолчанию («в сомнении — звони»).
7. **Перепланирование всех** (`rescheduleAll(reason)`; причины: `LOCKED_BOOT`, `BOOT`, `TIME_SET`, `TIMEZONE_CHANGED`, `PACKAGE_REPLACED`, `LOCALE_CHANGED`, `APP_LAUNCH`, `DEBUG`) идемпотентно: если сохранённый `nextTriggerAt ∈ (now − LATE_GRACE, now]` и `lastFiredAt < nextTriggerAt` — звонок пропущен (перезагрузка/выключение) → `CATCH_UP` на `now + 3 с`. `LATE_GRACE = 10 мин` (константа домена; более старые пропуски — M7, FR-REL-6). Ресиверы звонок **не стартуют**, только планируют (ADR-002 §5).
8. **Сериализация.** Все мутации расписания идут через один `AlarmEngine` (`:core:domain`) под общим `Mutex` — одновременные ресиверы не перетирают друг друга.
9. **Snooze в M1** — в движке и на экране звонка (кнопка по `Feature.SNOOZE`), с настройками по умолчанию 5 мин × 3 (редактор — M2). Лимит исчерпан → кнопки нет. `dismiss` обнуляет `snoozeCount` и возвращает `REGULAR`.
10. **Ошибки планирования.** `canScheduleExactAlarms() == false` или `SecurityException` → `schedule` возвращает `false`, логируется `SCHEDULE_FAILED`; ресивер не падает (при minSdk 34 и `USE_EXACT_ALARM` — страховка). Статус показывает экран здоровья (M3).

## Alternatives considered
* **Ставить в `AlarmManager` только ближайший будильник** — один `PendingIntent`, но тумблер/удаление требуют пересчёта «глобального следующего», а FR-LIST AC ожидает отмену конкретного интента. Отклонено.
* **`requestCode = id.toInt()` как идентичность** — работает на практике, но опирается на «id не вырастет»; URI-идентичность бесплатна и строга. Отклонено.
* **`Alarm.id: AlarmId?` / отдельный `AlarmDraft`** — nullable id протекает `!!` в планировщик; дубликат модели на ~15 полей ради одного поля. Отклонено в пользу `UNSAVED` (так же, как Room трактует 0).
* **gap по умолчанию `java.time` (02:30 → 03:30)** — противоречит FR-REL-4. Отклонено.
* **Snooze в M2** — пришлось бы позже менять схему runtime и логику перепланирования; snooze влияет на надёжность (отложенный будильник обязан пережить перезагрузку). Отклонено.

## Consequences
* (+) Детерминированный, покрываемый JVM-тестами расчёт (NFR-6); DST/TZ по построению.
* (+) Пропуск во время перезагрузки «догоняется» (≤ 10 мин).
* (−) `AlarmEngine` — единая точка; разрастание контролировать (M5 добавит миссии не сюда, а в хост).
* Проверка: unit — таблица кейсов калькулятора (дни недели, разовый, конец месяца/года, 29 февраля, Europe/Berlin gap/overlap 2026-03-29/2026-10-25, Asia/Kolkata, Australia/Lord_Howe (30-мин DST), Pacific/Apia, Pacific/Kiritimati), движок с фейками и подменяемым `Clock`; Robolectric — `ShadowAlarmManager`; R2, R3, R5, R6, R7, R9.

## Уточнения по итогам M1 (2026-10-03)
* **Идентичность `PendingIntent`** — data URI `balarm://alarm/<id>` при `requestCode = 0` (а не уникальный `requestCode`): без коллизий при любом `Long` id.
* **RESUME** (возврат звонка после падения, ADR-007 §7) не меняет runtime и не тратит snooze; разовый, не успевший выключиться до падения, выключается.
* **Degraded-звонок** (движок занят > 2 с или сбой хранилища): звонок с настройками по умолчанию, а срабатывание дописывается, когда движок освободится (`recordDegraded`) — иначе разовый зазвонил бы снова, а следующее срабатывание не было бы запланировано.
* **Пропуск дольше `LATE_GRACE`**: разовый выключается (`SkipReason.MISSED`), уведомление — M7 (FR-REL-6).
* `rescheduleAll` для системных событий и запуска UI вызывается через `SafeRescheduler`: ошибка целиком логируется (`RESCHEDULE_ALL_FAILED`), не роняет процесс; ресивер отпускает `goAsync` не позже 8 с.
